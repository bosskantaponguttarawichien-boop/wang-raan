# feat-150 — ฉากจำลอง 3D ลื่นไหล: วาดรอบเดียวต่อเฟรม

> หลักฐานวัดบนเครื่องอ้างอิง Windows 10 + NVIDIA GeForce GTX 1050 Ti (driver 32.0.15.8129),
> Chrome headless ผ่าน Playwright 1.64, production build, `--workers=1`
> renderer ที่เบราว์เซอร์รายงาน: `ANGLE (NVIDIA, NVIDIA GeForce GTX 1050 Ti (0x00001C82) Direct3D11 vs_5_0 ps_5_0, D3D11)`

## ต้นเหตุหลัก: หนึ่งเฟรมที่จอแสดง = วาดฉากซ้ำ 5–6 รอบ

`three-view.tsx` ตั้ง `frame = 0` ตอนเริ่ม `tick` เพื่อให้ `invalidate()` ที่ถูกเรียก**ระหว่าง**วาด
(จาก controller, store ของแสง, จาน/คราบบนโต๊ะ) ปลุกเฟรมถัดไปได้ แต่ท้าย `tick` จอง rAF ใบใหม่
**ทับ** ใบที่ `invalidate()` จองไว้ ใบเก่าไม่เคยถูกยกเลิกและยังทำงาน ยิ่งมีแหล่ง invalidate มากต่อเฟรม
ยิ่งจองซ้อนกันหลายใบ

วัดจากของจริงผ่าน diagnostic hook: ช่วงระหว่าง `tick` มัธยฐาน **7.2 ms** (118 ตัวอย่างใน 855 ms)
ขณะที่ภาพออกจริงทุก ~280 ms → ประมาณ 5–6 รอบต่อเฟรม

อาการข้างเคียงสองข้อที่เคยอธิบายไม่ได้ และหายไปพร้อมกัน:
- **AdaptiveQuality ไม่เคยลดคุณภาพ** (`level: 0` ตลอด แม้ผู้ใช้เห็น 3.5 fps) เพราะมัธยฐานที่ตัววัดเห็น
  คือ 7 ms ซึ่ง "เร็วกว่าเป้า 38 ms" จึงไม่มีเหตุให้ลด
- **ย่อ viewport เป็น 464×160 แล้วเวลาเฟรมไม่ลดเลย** (280 ms เท่าเดิม) เพราะไม่ใช่ภาระ fill rate
  แต่เป็นงาน CPU ที่ถูกทำซ้ำ

**แก้:** ทุกจุดจองเฟรมผ่าน `schedule()` เดียวที่จองได้ใบเดียว (`if (!frame)`)

## ผลวัดฉากหนาแน่น 80 ที่นั่ง (ลูกค้า 60–66 + พนักงาน 8, draw calls ~680)

| สถานะโค้ด | median/เฟรม | fps |
|---|---|---|
| ต้นเซสชัน (HEAD เดิม) | 860 ms | 1.2 |
| หลังแก้เมทริกซ์ + layout | 420 ms | 2.4 |
| หลังแก้ shadow proxy / quality / overlay | 280 ms | 3.6 |
| **หลังแก้การจองเฟรมซ้อน** | **20 ms** | **50 (เพดาน vsync)** |

ทุกตัวเลขวัดขณะการจำลองเดินจริง (`running: true`, เวลาจำลองเดิน 3.2 วินาทีใน 3 วินาทีที่ 1×)
ที่คุณภาพขั้นสูงสุด (`level: 0`, เงาตัวละครเปิด, shadow map 2048)

## แก้ความเข้าใจผิดในหลักฐานของ feat-123

หลักฐานเดิมของ feat-123 ระบุว่าฉากหนาแน่นได้ **median 50.0 fps / p95 49.8 fps บนเครื่องอ้างอิง**
ตัวเลขนั้นไม่ได้วัดฉากที่กำลังจำลอง: controller รุ่นก่อน feat-137 **หยุดภาพเอง** เมื่อวาดไม่ทัน
พอฉากนิ่ง ลูป 3D ก็หยุดทำงานต่อเฟรม แต่ลูปวัดของเทสต์ยังเดินตาม vsync ที่ 20 ms จึงได้ "50 fps"
ของฉากที่ค้างอยู่

ยืนยันด้วยการรันคอมมิต `2f2fb34` (feat-123 เสร็จ) ซ้ำบนเครื่องเดียวกันวันนี้: ช่วงเติมคนจบด้วย
`stalled: 21` คือเวลาจำลองไม่เดินมา ~10 วินาทีก่อนเริ่มวัด

เทสต์ `restaurant-animation-stutter.spec.ts` ของ feat-137 บันทึก `simSecondsAdvanced` และ
`selfPauses` ไว้ทุกช่วงวัด ตัวเลขจากไฟล์นั้นจึงไม่มีช่องให้เกิดความเข้าใจผิดแบบเดียวกันอีก

## เครื่องมือใหม่สำหรับ QA (read-only, ติดตั้งเฉพาะเมื่อมี `__wangraanDiagnostics`)

`hook.quality()` คืนสถานะที่ใช้วาดอยู่จริง: `level`, `characterShadows`, `shadowMapSize`,
`pixelRatio` ที่ renderer ใช้, `shadowAutoUpdate`, `visibleShadowProxies`, `sampler`
(ช่วงเฟรมล่าสุดที่ตัววัดเห็น + ความคืบหน้าช่วงวัด) และ `sceneInstances`

ตัวเลข fps ที่ไม่มีสถานะคุณภาพกำกับเชื่อถือไม่ได้ — `sampler` คือสิ่งที่ชี้ตัวต้นเหตุรอบนี้

## เทสต์แสงที่เคยล้ม: พิกเซลเดียวกะพริบ ไม่ใช่เวลาหรือแสงเดิน

ข้อ "แสงอิงเวลาเปิดร้าน เดินตามจำลอง และหยุดเมื่อพัก โดยไม่อิงเวลาเครื่อง" ล้มในชุดรวม 2 รอบ
แต่ผ่านเมื่อรันเดี่ยว จึงไล่ไทม์ไลน์หลังกดหยุด (ถ่ายภาพทุก 0.5 วินาที 18 วินาที):

- พิกเซลที่เปลี่ยนคือ **จุดเดียว** ที่ตำแหน่ง (572, 215) กะพริบสลับไปมาแบบสุ่ม **ทั้งก่อนและหลัง**
  กระโดดเวลาเครื่อง — พิกเซลที่เหลือทั้ง 532,416 จุดนิ่งสนิท, CSS animation ที่ทำงาน 0 ตัว, console error 0
- `resolveRestaurantSolarUtcMs()` ใช้วันที่อ้างอิงที่ตั้งไว้ ไม่ใช่วันที่ของเครื่อง (clock.ts:27) —
  เวลาเครื่องจึงไม่เข้าสมการแสงจริงตามที่เทสต์ต้องการตรวจ

เทสต์เดิมเทียบภาพแบบไบต์ต่อไบต์ (`Buffer.equals`) จึงล้มจากพิกเซลเดียว แก้เป็น:
1. รอให้ภาพนิ่งจริงก่อนถ่ายภาพอ้างอิง (`settledShot`) — กันการแข่งจังหวะกับโมเดล GLB ที่โหลดเสร็จ
   หลังกดหยุด (ตัวละครต้องปรากฏขึ้น ไม่ใช่หายไป จึงเป็นการเปลี่ยนที่ถูกต้อง)
2. เทียบแบบ "ไม่มีการเปลี่ยนที่ตาเห็น": เพดาน 266 จุด (0.05% ของภาพ) และบันทึก
   `movedPixelsWhilePaused` ลงหลักฐานทุกครั้ง — แสงที่ขยับจริงเปลี่ยนพิกเซลเป็นพันจุด

ผลรันซ้ำ 3 รอบ: ผ่านทั้ง 3 ด้วย `movedPixelsWhilePaused` = 1, 1, 0
