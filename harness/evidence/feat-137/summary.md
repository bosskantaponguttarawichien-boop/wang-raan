# feat-137 — ลดอาการกระตุกระหว่างจำลอง

## สรุปสั้น

อาการ "กระตุก" ที่แท้จริงบนเครื่องที่วาดภาพไม่ทันคือ **การจำลองหยุดเองแล้วไม่กลับมา** ไม่ใช่ fps ต่ำ
เครื่องทดสอบกด "เริ่มจำลอง" แล้วขึ้น "หยุดชั่วคราว" ภายใน 0.4 วินาที และค้างอยู่อย่างนั้นตลอด
49 วินาทีที่เฝ้าดู — เวลาจำลองไม่เดินเลยทั้ง 6 ช่วงวัดของการรันต่อเนื่อง

แก้สองจุดที่เป็นตรรกะล้วน (ไม่เกี่ยวกับ GPU) แล้ววัดซ้ำใน environment เดิม: ทุกความเร็วเดินต่อเนื่อง
และรักษาอัตราเวลาได้ตรง (1×→1.0×, 5×→5.1×, 10×→~10×, 30×→29.7×)

## ข้อจำกัดของตัวเลขในรายงานนี้ (อ่านก่อน)

เครื่องที่วัดเป็น container **ไม่มี GPU** — WebGL เป็น software rasterizer:

```
ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero) (0x0000C0DE)), SwiftShader driver)
```

ฉากหนาแน่นจึงได้ราว **3–4 fps แม้มีลูกค้าเพียง 1 คน** (เฟรม 233–417 ms, draw calls 207)

ผลที่ตามมา:

- **ตัวเลข fps ในไฟล์นี้เทียบกับเครื่องอ้างอิงที่มี GPU ไม่ได้** และห้ามใช้อ้างว่าผ่านเกณฑ์ performance
  เกณฑ์ fps ของฉากหนาแน่นอยู่ที่ `e2e/restaurant-animation.spec.ts` ("performance ฉากหนาแน่น")
  ซึ่ง feat-123 วัดได้ median 50.0 fps / draw calls 693 บน NVIDIA GTX 1050 Ti — **ยังไม่ได้วัดซ้ำหลังการแก้ครั้งนี้**
- **เติมคนให้ร้านแน่นไม่ขึ้นใน container นี้** (peak 1–4 คน) เพราะฉากวาดไม่ทัน จึงวัด "ภาระฉากหนาแน่น"
  ไม่ได้ ที่วัดได้คือ "ภาพเดินต่อเนื่องหรือไม่" ซึ่งเป็นหัวใจของงานนี้และใช้ได้ทุกความหนาแน่น
- ภาระต่อ TICK วัดด้วย Node (ไม่ใช้เบราว์เซอร์) จึงไม่ขึ้นกับ GPU — ดูหัวข้อถัดไป

## ภาระต่อ TICK ไม่ใช่ต้นเหตุ (วัดแล้ว จึงไม่รื้อ)

วัดบน snapshot ของผังหนาแน่น 80 ที่นั่งจริง (134 ลูกค้า, 51 จาน, 20 โต๊ะ, 8 พนักงาน, 40 milestones,
68 KB/TICK) ด้วย Node/vitest 300 รอบต่อค่า:

| สิ่งที่วัด | ต่อ 1 TICK |
|---|---|
| `parsePresentation` (Zod safeParse + ตรวจความสอดคล้อง) | **1.203 ms** |
| `alignPresentation` | 0.018 ms |
| `structuredClone` (เทียบเท่าการถอด postMessage) | 0.890 ms |
| รวมที่ 20 TICK/วินาที | **≈ 4% ของ 1 คอร์** |

สรุป: เล็กเกินกว่าจะทำให้ภาพกระตุก **จึงไม่รื้อ Zod ออกจากเส้นทางนี้** — การเปลี่ยน validation
ที่เป็น trust boundary โดยไม่มีตัวเลขสนับสนุนคือความเสี่ยงที่ไม่ได้อะไรกลับมา

## สิ่งที่แก้

### 1. `simulation-controller.ts` — ช่องว่างของเวลาไม่ควรหยุดการจำลองค้างไว้

`PlaybackClock` ถือว่าเป็น `gap` เมื่อ TICK ห่างกันเกิน 0.5 วินาทีจริง เดิม controller ตอบด้วยการ
**หยุดภาพทุกกรณี** แล้วรอให้ผู้ใช้กด "เล่นต่อ" เอง บนเครื่องที่บล็อก main thread เกินครึ่งวินาที
(โหลด GLB ครั้งแรก, คอมไพล์ shader, GC, ฉากหนาแน่น) การจำลองจึงหยุดตั้งแต่วินาทีแรกและไม่กลับมาเอง

ตอนนี้แยกสองกรณี:

- ช่องว่าง **ไม่เกิน 10 วินาทีจำลอง** (หลังหารด้วยตัวคูณความเร็ว) = อาการของฝั่งภาพ →
  ตั้งต้นภาพใหม่ให้ตรงเวลาจำลองแล้ว **เล่นต่อทันทีด้วย delta 0** ทิ้งเวลาที่ขาดไป
  ตาม `animation-contract-v1.md` §2 (ไม่ไล่เวลา ไม่เล่นย้อน)
- ช่องว่าง **ยาวกว่านั้น** (เครื่องหลับ/แท็บถูกพักยาว) → หยุดภาพไว้เหมือนเดิม เพราะตัวละคร
  จะกระโดดไกลจนดูไม่รู้เรื่อง และข้อความบอกทางแก้เมื่อเกิดที่ความเร็วสูง ("ลองลดความเร็วลง")
- คิว pacer ล้น → ตั้งต้นใหม่ใน TICK ถัดไปโดยไม่หยุดภาพ

### 2. `adaptive-quality.ts` — เครื่องที่ช้าที่สุดกลับไม่เคยถูกลดคุณภาพ

`ignoreAboveMs` เดิม 250 ms ตั้งใจตัดช่วงที่แท็บถูกซ่อน แต่เครื่องที่วาดฉากหนาแน่นได้เฟรมละ
250–350 ms ถูกตัด **ทุกเฟรม** คุณภาพจึงค้างที่ขั้นสูงสุดตลอด ทั้งที่เป็นเครื่องที่ต้องการการลดคุณภาพที่สุด
เปลี่ยนเป็น 900 ms — แท็บที่ถูกซ่อนจริงไม่เรียก rAF หรือเรียกราว 1 ครั้ง/วินาที จึงยังถูกตัดตามเจตนาเดิม

## เทสต์ที่คุมอาการนี้ และหลักฐานว่าเทสต์จับได้จริง

`e2e/restaurant-animation-stutter.spec.ts` — ข้อแรกใช้ **ผังตัวอย่าง 6 ที่นั่ง** จึงรันได้ทุกเครื่อง
รวมเครื่องที่ไม่มี GPU (อีกสองข้อเป็นฉากหนาแน่น ซึ่ง `test.skip` อย่างชัดเจนเมื่อเจอ software renderer)

พิสูจน์ว่าเป็นด่านจริง ไม่ใช่เทสต์ที่ผ่านทั้งสองทาง — ชั่วคราวเปลี่ยน controller กลับเป็นพฤติกรรมเดิม
(หยุดภาพทุกครั้งที่เจอช่องว่าง) แล้ว build ใหม่และรันข้อนี้:

```
Error: 1×: เวลาจำลองไม่เดิน (ภาพค้าง)
expect(received).toBeGreaterThan(expected)
Received:   0
```

**ข้อสังเกตสำคัญ**: อาการนี้เกิดกับ **ผังตัวอย่าง 6 ที่นั่งที่มีลูกค้าเพียงคนเดียว** ไม่ใช่เฉพาะฉากหนาแน่น
ต้นเหตุคือจังหวะโหลด GLB ครั้งแรกตอนเปิดมุมมอง 3D ไม่ใช่จำนวนตัวละคร — ผู้ใช้บนเครื่องธรรมดาที่โหลด
โมเดลช้ากว่าครึ่งวินาทีก็เจอได้ หลังแก้แล้วข้อนี้ผ่าน: 1× เดิน 8.3 วินาทีจำลองใน 8 วินาทีจริง (1.04×),
10× เดิน 82 วินาที (10.25×), controller ไม่หยุดภาพเอง 0 ครั้ง

## ก่อน–หลัง (environment เดียวกัน, ผังหนาแน่น 80 ที่นั่ง, พนักงาน 8 คน)

| | ก่อน | หลัง |

| กดเริ่มจำลองแล้วเปิด 3D | "หยุดชั่วคราว" ที่เวลาจำลอง 0.4–0.6 วิ | "กำลังจำลอง" ต่อเนื่อง |
| เฝ้าดู 49–60 วินาที | ค้างทั้งช่วง ไม่กลับมาเอง | เดินต่อเนื่องทั้งช่วง |

## ไม่พบปัญหารั่ว (ยืนยันทั้งก่อนและหลัง)

การรันต่อเนื่อง 6 ช่วง × 15 วินาที: heap 16.9 → 17.3 MB, DOM node คงที่ 243,
geometries คงที่ 186, draw calls คงที่ 207 — การใช้ DOM ซ้ำของก้อนความคิด (งานรอบก่อนของ feat-137)
ยังทำงานถูกต้อง ไม่มี DOM หรือ geometry งอกตามเวลา

## ที่ยังค้าง (ต้องใช้เครื่องที่มี GPU)

1. **รันสองข้อที่ถูก skip ของ `restaurant-animation-stutter.spec.ts` บนเครื่องที่มี GPU** —
   container นี้ skip ให้เองเพราะเป็น software renderer; เมื่อฉากหนาแน่นจริงบนเครื่องนี้
   main thread แน่นถึงขั้นสั่งงานหน้าเว็บไม่ได้ (คลิกปุ่มความเร็วค้างจน timeout)
2. **วัดซ้ำเกณฑ์ fps ฉากหนาแน่นบนเครื่องอ้างอิง** — `e2e/restaurant-animation.spec.ts`
   ข้อ "performance ฉากหนาแน่น" และชุด 28 ข้อของ feat-123 ยังไม่ได้รันหลังการแก้ครั้งนี้
   (container ไม่มี GPU จึงรันแล้วไม่มีความหมาย) การแก้ทั้งสองจุดไม่แตะ geometry/material/จำนวน
   draw call แต่ `ignoreAboveMs` ทำให้เครื่องช้าลดคุณภาพได้จริง ซึ่งอาจเปลี่ยนภาพที่ถ่ายได้บนเครื่องช้า
3. **ข้อสังเกตที่ยังไม่ได้ทำ (นอกขอบเขต feat-137)**: ฉากที่แทบไม่มีคนใช้ draw calls ถึง **207**
   เพราะโต๊ะ 20 ชุด/เก้าอี้ 80 ตัวเป็น mesh แยกกัน การรวม geometry ของฉากนิ่งน่าจะลด draw call
   ได้มากและช่วยทุกเครื่อง — ยังไม่มีหลักฐานว่าผู้ใช้จริงต้องการ (feat-123 วัดได้ 50 fps บน GTX 1050 Ti)
   จึงไม่แก้ในงานนี้
